1. The network (modules/vpc)

Every EKS design starts with IP planning, because on EKS each pod gets a real VPC IP address from the subnet its node is in (the AWS VPC CNI plugin). Run out of IPs and pods stay Pending even when nodes have free CPU.

PieceValueWhy this choice
VPC CIDR10.20.0.0/16 (65,536 IPs)Room for DR VPCs later with no overlap (Germany could be 10.30.0.0/16). Overlapping CIDRs block VPC peering and Transit Gateway.
Public subnets3 × /24 (251 usable each)Only load balancers and the NAT live here. Small is fine.
Private subnets3 × /20 (4,091 usable each)Nodes and pods live here. AWS reserves 5 IPs per subnet.
AZs3 (from aws_availability_zones)Survives losing one AZ. EKS needs at least 2.
NAT1 gateway (dev)~$0.056/h each. Prod uses one per AZ so an AZ failure doesn't cut off the other AZs' outbound traffic.
S3 endpointGateway typeFree. Image layers from ECR are stored in S3, so this cuts NAT data charges.

How traffic flows

  • Inbound: internet → Internet Gateway → ALB in the public subnets → pod IP in a private subnet. Nothing in a private subnet has a public IP.
  • Outbound from a pod: private route table 0.0.0.0/0 → NAT → NAT (public subnet) → IGW. The NAT translates the private IP to its Elastic IP.
  • To S3: the route table has a prefix-list route to the gateway endpoint, so S3 traffic never touches the NAT.

Subnet tags: how Kubernetes finds subnets

TagRead byMeaning
kubernetes.io/role/elb = 1LB controllerPut internet-facing ALBs/NLBs here.
kubernetes.io/role/internal-elb = 1LB controllerPut internal load balancers here.
karpenter.sh/discovery = <cluster>KarpenterLaunch new nodes in these subnets (also used on the security group).

Small security details that interviewers like

  • map_public_ip_on_launch = false even on public subnets: no instance gets a public IP by accident.
  • aws_default_security_group with no rules: every VPC has a default SG that allows all traffic between its members. Taking it over and leaving it empty means nothing can silently use it (a CIS benchmark check).
  • Interface endpoints (ECR, STS, SSM, logs) are a variable, off in dev. Each costs ~$0.013/h per AZ: 7 services × 3 AZs is about $6/day. That's a real cost trade-off you can explain.
Interview one-liner: "I sized private subnets as /20s because the VPC CNI gives every pod a VPC IP. Public subnets only hold load balancers and NAT, so /24 is enough. Dev uses one NAT to save money; prod uses one per AZ to remove the single point of failure."

2. Why three stacks and three state files

network → eks → platform. Each has its own backend.tf key in the same S3 bucket, and later stacks read earlier ones with terraform_remote_state.

  • Blast radius: a mistake in a Helm chart can't plan a change to the VPC.
  • Speed: smaller state = faster plan, fewer locks.
  • The provider chicken-and-egg problem: the Helm and kubectl providers need the cluster endpoint at plan time. If the cluster and the Helm releases are in one stack, the first plan fails because the cluster doesn't exist yet. Splitting them solves it.
  • Destroy in reverse (platform, eks, network). Delete Ingresses first, or the ALBs the controller created keep ENIs in the subnets and the VPC destroy hangs.

3. The EKS cluster (modules/eks)

Control plane

EKS runs the API server and etcd for you across 3 AZs in an AWS-owned account. Your VPC only sees ENIs that EKS places in your private subnets; that's how nodes talk to the API privately.

SettingOur valueWhat it does
endpoint_private_accesstrueNodes reach the API through the ENIs, never the internet.
endpoint_public_access + public_access_cidrstrue, your IP /32You can run kubectl from your laptop; the rest of the internet can't even reach the API. The tfvars validation rejects 0.0.0.0/0.
encryption_configKMS key, secretsEnvelope encryption: each Secret is encrypted with a data key, and that data key is encrypted with your KMS key. A copy of etcd alone is useless.
enabled_cluster_log_typesapi, audit, authenticatoraudit answers "who deleted that deployment?". We create the log group first so Terraform owns retention (30 days); otherwise EKS creates it with no expiry.
upgrade_policySTANDARDStandard support is 14 months. After that, extended support costs $0.60/h instead of $0.10/h (6×). STANDARD means AWS auto-upgrades you instead of billing you.

Who can log in: access entries (not aws-auth)

authentication_mode = "API" uses EKS access entries, the replacement for the old aws-auth ConfigMap. Access is managed through the AWS API and Terraform, so a bad YAML edit can no longer lock everyone out of the cluster. The creator gets admin automatically; admin_principal_arns adds more people with AmazonEKSClusterAdminPolicy.

System node group (managed)

  • 2 × t3.medium, on-demand, AL2023, label node-role/system=true. Runs CoreDNS, the LB controller and Karpenter itself. Karpenter must not run on nodes it manages, or it could delete its own node.
  • ignore_changes = [desired_size]: Terraform sets the size once and doesn't fight an autoscaler afterwards.
  • Launch template, IMDSv2 required, hop limit 1: the instance metadata service holds the node role's credentials. A pod is one network hop further away than the node, so with hop limit 1 its packets never reach IMDS. A compromised pod can't steal the node's IAM role. This is a classic Zero Trust interview point.
  • Encrypted gp3 root volumes; AmazonSSMManagedInstanceCore so you use Session Manager, never SSH keys.

Add-on ordering (a real-world gotcha)

Add-onWhenWhy
vpc-cni, kube-proxy, eks-pod-identity-agentBefore nodesNodes stay NotReady until a CNI exists; Pod Identity must be ready before pods need AWS credentials.

Interview one-liner: "The API is private for nodes and public only for my IP. Secrets are envelope-encrypted with a customer KMS key, audit logs go to CloudWatch, access uses access entries instead of aws-auth, and nodes enforce IMDSv2 with hop limit 1 so pods can't steal node credentials."

4. Giving pods AWS permissions: IRSA vs Pod Identity

IRSA (2019)

  1. Cluster has an OIDC issuer; you register it as an IAM OIDC provider.
  2. Role trust policy names that provider and the exact system:serviceaccount:ns:name.
  3. Service account annotated with the role ARN.
  4. The SDK calls sts:AssumeRoleWithWebIdentity with the projected token.

Downside: each role's trust policy is tied to one cluster's OIDC URL, so a new cluster (DR!) means editing every role.

Pod Identity (2023, what we use)

  1. Role trusts the service principal pods.eks.amazonaws.com.
  2. An association (cluster + namespace + service account → role) is created by the EKS API.
  3. The eks-pod-identity-agent DaemonSet hands credentials to the pod.

Upside: same role reused across clusters; no annotations; no OIDC provider per cluster. We still create the OIDC provider so IRSA works for tools that need it (ADR 0004).

Three roles today: Karpenter (launch/terminate EC2, read SQS), AWS Load Balancer Controller (create ALBs, target groups, security group rules), EBS CSI (create/attach volumes). Each pod gets only its own permissions: least privilege per workload, not per node.

5. The platform stack (environments/dev/platform)

AWS Load Balancer Controller

Watches Ingress and Service type=LoadBalancer objects and creates real ALBs/NLBs. With target-type: ip the ALB sends traffic straight to pod IPs (possible because pods have VPC IPs), skipping NodePort and kube-proxy hops. In the diagram, this is the "ALB, TLS entry point" box.

Karpenter (just-in-time nodes)

  1. A pod is Pending because no node has room.
  2. Karpenter reads the pod's needs (CPU, memory, arch, zone, tolerations) and picks the cheapest instance type that fits from the NodePool rules.
  3. It calls EC2 directly (no Auto Scaling group), so the node usually joins within about a minute.
  4. Consolidation (WhenEmptyOrUnderutilized, after 1 min): it removes empty nodes and repacks pods onto fewer or cheaper nodes.
  5. Spot interruptions: AWS sends a 2-minute warning to EventBridge → SQS. Karpenter reads the queue, cordons and drains the node, and launches a replacement before the instance disappears.
Our NodePool ruleReason
capacity-type: spot, on-demandSpot is up to ~70% cheaper; on-demand is the fallback when no spot capacity exists.
Families c, m, t; generation > 4; size medium–xlargeModern instances, no huge surprise nodes in dev.
limits.cpu = 16Cost guard rail: a runaway Deployment can't launch 50 nodes.
expireAfter: 720hNodes are replaced every 30 days, so they always run a recent, patched AMI.
EC2NodeClass: al2023@latest, IMDSv2 hop 1, encrypted gp3Same hardening as the system nodes. Pin the AMI version in prod so upgrades are deliberate.

HPA + Karpenter together (diagram box "HPA + Karpenter")

metrics-server collects pod CPU/memory. The HPA scales pods (for example 2 → 6 replicas at 70% CPU). New pods that don't fit go Pending, and Karpenter scales nodes. When load drops, the HPA removes pods and Karpenter consolidates the empty nodes. Two layers, each doing one job.

Interview one-liner: "HPA scales pods using metrics-server; Karpenter scales nodes by watching for Pending pods and picking the cheapest instance that fits. Spot interruptions come through EventBridge and SQS so Karpenter can drain nodes before AWS reclaims them, and a CPU limit on the NodePool caps cost."

7. Interview questions with model answers

Q1. Why do EKS clusters run out of IP addresses, and how did you plan for it?
The VPC CNI gives each pod an IP from the node's subnet, and each instance type has an ENI/IP limit. I made private subnets /20 (about 4,000 IPs each across 3 AZs). If it ever gets tight, the options are prefix delegation (a /28 per ENI slot) or a secondary CIDR (for example 100.64.0.0/16) with custom networking.
Q2. Public subnet vs private subnet: what actually makes a subnet "public"?
Only its route table: a 0.0.0.0/0 route to an Internet Gateway. Private subnets route 0.0.0.0/0 to a NAT gateway, which allows outbound connections but no inbound ones.
Q3. How do you secure the EKS API endpoint?
Private access on so nodes stay inside the VPC; public access either off or restricted to known CIDRs; authentication through IAM, authorization through access entries and RBAC; audit logs to CloudWatch.
Q4. What is envelope encryption for Secrets, and why does it matter?
Kubernetes Secrets are only base64 by default. With a KMS provider, each Secret is encrypted with a data key, and the data key is encrypted with a KMS key you control. Without KMS permission, an etcd backup is unreadable, and every decrypt shows up in CloudTrail.
Q5. aws-auth ConfigMap vs access entries?
aws-auth is a YAML file inside the cluster: one bad edit can lock everyone out, and it isn't visible from IAM. Access entries are an EKS API resource, managed by Terraform, auditable in CloudTrail, with managed policies like AmazonEKSClusterAdminPolicy.
Q6. IRSA vs EKS Pod Identity?
Both give a single service account its own IAM role. IRSA uses an OIDC provider and AssumeRoleWithWebIdentity, and its trust policy is tied to one cluster. Pod Identity uses an agent plus associations, trusts pods.eks.amazonaws.com, and the same role can serve many clusters, which helps with DR.
Q7. Why IMDSv2 with hop limit 1?
IMDS returns the node role's temporary credentials. IMDSv2 needs a session token (PUT request), which blocks SSRF-style GET attacks. Hop limit 1 means packets from inside a pod network namespace expire before reaching IMDS, so pods must use their own Pod Identity role.
Q8. Karpenter vs Cluster Autoscaler?
Cluster Autoscaler resizes pre-defined Auto Scaling groups, so you pick instance types in advance. Karpenter looks at pending pods and launches the best-fitting, cheapest instance directly through EC2, consolidates underused nodes, and handles spot interruptions. It's usually faster and cheaper.
Q9. Why split Terraform into network, eks and platform stacks?
Smaller blast radius, faster plans, separate locks, and the Helm/Kubernetes providers need a cluster that already exists at plan time. Outputs flow forward through terraform_remote_state.
Q10. Something you caught that would have cost money?
The plan said Kubernetes 1.33, which by November 2026 is in extended support at $0.60/h instead of $0.10/h. I moved to 1.36, set upgrade_policy = STANDARD, and checked the Karpenter compatibility matrix (1.36 needs Karpenter ≥ 1.13; we use 1.15.3).
